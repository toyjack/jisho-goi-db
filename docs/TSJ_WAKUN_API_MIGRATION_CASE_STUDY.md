# 《新撰字鏡》和訓データベース：API 迁移中的检索相关性劣化与修复

> 记录范围：2026-08-28〜2026-08-29，Tsj-Wakun（新撰字鏡和訓データベース）模块从 Supabase 迁移到
> hdicviewer-rebuild 公开 API 后的一次实际排障过程。相关提交：`9118613`、`2eef1d8`、`03c9603`
> （另有一次无关模块 Bunmei 的数据/UI 修复 `da090de`，测试过程中顺带发现，本文档不展开）。

## 1. 背景：一次"看似完成"的架构迁移

Tsj-Wakun 模块此前直连 Supabase（PostgreSQL）查询《新撰字鏡》和訓数据。项目决定将其改为调用作者自
己维护的另一个仓库 `hdicviewer-rebuild` 暴露的公开 REST API（`/api/v1`），原因是长期架构方向要收
敛到这个新 API，而不是继续依赖 Supabase 直连。

迁移涉及两个需要产品侧拍板的设计决策，均已确认：

1. **详情页寻址方式变更**：新 API 的最小可查询单元是"条目记录"（`recordId`，字符级），而不是旧表
   里"一行一条和訓"的 `wakunId`。一条 `recordId` 下可能挂 0～N 条和訓记录（`wakunParts[]`）。详情
   页路由因此从 `/tsj-wakun/[wakunId]` 改为 `/tsj-wakun/[recordId]`，不做旧链接兼容。
2. **结果分页语义变更**：新 API 的搜索分页按"命中的条目数"而非"命中的和訓行数"，结果页因此展示为
   "一条命中记录 → 展开其下所有匹配和訓行"的结构。

从功能清单上看，迁移在 2026-08-28 已经"完成"：字段改名、种别/品词/字数下拉筛选、日国 ID 到 URL 的
拼接、异体字检索开关全部接入完毕，typecheck/lint 通过。但这只验证了"代码能跑"，没有验证"结果对
不对"——这正是本文档的核心。

## 2. 核心问题：搜索结果里混入大量无关行

用户实际使用时报告：搜索"見出し語（享和本）"字段（`kyowa_entry_text`）为"乱"，返回的结果里大部
分和"乱"没有任何关系。

### 2.1 根因

新 API 的 `/search` 端点只提供 `field=all|headword|definition|reading` 四种字段范围，**没有对应
"享和本见出し"（`kyowa_entry_text`）或"万叶假名定义"（`def_manyogana`）的专属选项**。这两类查询只
能退化为 `field=all`（全字段检索），于是查询字符串出现在记录的任意字段——包括与用户实际想搜的字
段完全无关的汉文校注/按语文字——都会被判定为"命中"。

命中之后，API 返回的 `matchedPartIds` 试图把"记录级命中"关联回具体的某一条和訓行，但这个关联本身
不可靠：它有时指向和訓行自己的 ID 空间，有时指向记录内部字符位置的另一套 ID 空间，两者形式相近但
不能通用；即便字段限定为 `headword`，也会出现同名但语义不同的字段被一并归为同一 `fieldRole` 的情
况。旧代码在"ID 对不上任何和訓行"时采取的兜底策略是**把该记录下所有和訓行原样展示**——这个兜底原
本是为了不漏掉真正相关的结果，实际却成了噪声的主要来源。

一个可复现的具体案例：搜索"乱"命中了记录 `s0207a602`，原因是该记录附带的校注文字里出现了"攪乱"一
词；而该记录下真正的和訓行、其"享和本见出し"字段实际内容是"𥉾⿰目⿱羽𱥯"，与"乱"毫无关系，却因为
兜底策略被一并展示出来。

### 2.2 修复

不再把"服务端返回的 ID 归属"当作展示与否的唯一依据，而是在客户端对每一条候选行做二次校验：只有该
行**实际检索字段**（如 `kyowaEntryText`）里真的包含查询字符串，才允许进入结果列表。对开启了"异体
字检索"（`variant_search`）的查询豁免这一字面量校验——因为服务端不会告知客户端某一行具体是通过哪
个异体字匹配上的，客户端没有能力做等价性验证；这是目前有意保留、待未来 API 补充信息后收紧的已知
限制。

修复效果（真实生产数据，非模拟）：同一个"乱"查询，从 7 行（其中 6 行无关）收敛到 1 行（`乱亂`，
唯一实际相关的结果）。

## 3. 附带发现：部署前置检查的必要性

功能修好之后，按计划推送前，先用 Vercel CLI 在本地核对生产环境变量，发现新 API 所需的
`HDIC_API_BASE_URL` 从未配置到 Vercel 的任何环境（Production/Preview/Development）。这类缺失不会
在构建阶段报错，代码里的错误处理会把它包装成一条"检索中发生错误"的友好提示——功能性失效，但不会
触发通常意义上的告警。用 `vercel env add` 补齐后，用 `vercel pull` + `vercel build --prod` 在本地
按真实生产环境变量完整构建一遍，确认无误后才推送。

## 4. 两个小修复：外部链接的正确性与可读性

- 详情页指向《日本国語大辞典》（日国）个人版/图书馆版的链接路径格式有误，已按确认后的真实格式修正
  为 `/display/?lid={id}`。
- 详情页所有文字链接原先使用主题色 `link-primary`，而该自定义 DaisyUI 主题的 `primary`
  （`#F2E96D`，浅黄）与页面背景 `base-100`（`#F2F2EB`，近白）几乎没有对比度，链接几乎不可辨识；改
  为与站内其它模块一致的 `link-hover` 样式。

## 5. 方法论小结

1. **契约（行为）测试比读代码 diff 更能发现"结果存在但语义不对"这类问题。** 本项目 8 个数据库模
   块共享"搜索 → 结果列表 → 详情页"的模式，用端到端契约测试（Playwright）覆盖这个模式，比逐行审查
   实现细节更容易暴露"检索到了，但检索错了"的缺陷——这类缺陷不会让程序崩溃，只会让结果安静地变差。
2. **"ID 对得上"不等于"字段语义对得上"。** 这是本次相关性 bug 的核心教训：跨系统集成时，上游返回
   的关联 ID 即便格式正确、查询能跑通，也不能替代对目标字段语义的直接校验，尤其是在上游 API 的能
   力边界（没有某个字段的专属检索）迫使你退化到更宽泛的查询范围时。
3. **上线前用云平台的本地 CLI 工具重放一次生产构建，是低成本、高杠杆的部署前检查。** 一个环境变量
   的缺失足以让一个功能模块在生产环境静默失效；这类问题在本地开发环境（`.env` 通常配置完整）几乎
   不可能被发现，只有对照真实的生产环境配置才能提前拦截。
